# Self-Test Design (программы как устройства)

## Философия

Надёжные устройства не тестируют «снаружи» через дырочку в корпусе — тестируемость
встроена в схему: BIST (Built-In Self-Test), POST (Power-On Self-Test), JTAG,
коды неисправностей, watchdog. Тест — не последний этап перед сдачей, а часть
архитектуры, продуманная одновременно с самой функциональностью.

Применяй это мышление к программам:
- Модуль/сервис/игра должен уметь **сам** сказать «я в порядке» или «вот код неисправности N»,
  без необходимости человека тыкать кнопки и смотреть глазами.
- Тестируемость — не отдельная задача «допишем тесты потом», а требование к архитектуре
  с первого дня: если код трудно тестировать снаружи, его нужно перепроектировать, а не
  обвешивать костылями мока.

## Золотое правило тестирования (главное, что нужно помнить всегда)

> Не просто проверяйте, что программа делает то, что вы хотите —
> проверяйте, что она **не делает того, чего вы не хотите**.

Практические следствия:

1. **Проверка результата — это не только "правильное значение получено".**
   Нужно проверять и то, что *больше ничего не изменилось*. Легко написать тест
   на "функция вернула 42". Гораздо реже проверяют "а поменялось ли что-то ещё —
   другое поле состояния, глобальная переменная, файл на диске, счётчик, которого
   тест не ждал".
2. **Ищи глючные переходы между состояниями.** Баги чаще живут не в стационарных
   состояниях, а в переходах между ними (esp. при гонках, повторных вызовах,
   отмене операции на середине, неожиданном порядке событий).
3. **Идеальный вывод теста похож на таблицу переходов состояний**
   (state transition table): для пары (текущее состояние, событие) — заранее
   зафиксированные ожидаемые (новое состояние, побочные эффекты, вывод), и тест
   сверяет ФАКТИЧЕСКИЙ снимок целиком, а не только то поле, которое разработчик
   решил проверить. См. `references/state-transition-testing.md` — там методика
   и пример таблицы.

Держи это правило перед глазами при написании любого self-test блока ниже —
без него легко построить BIST, который бодро зелёный, но ловит только то, что
разработчик и так предвидел.

## Архитектурный паттерн: стандартный тест-порт (аналог JTAG)

Не оборачивай тестами каждый модуль по-своему — определи **один контракт**,
одинаковый для всех модулей/игр/сервисов в проекте, чтобы внешний "тестовый стенд"
(CI-скрипт, headless-браузер, оркестратор) не знал ничего о внутреннем устройстве
конкретного модуля, только про сам контракт.

Минимальный контракт (псевдокод, реализуется на любом языке):

```
TestPort {
  markReady()                     // модуль прошёл boot/инициализацию (аналог POST)
  heartbeat()                     // "я жив" — зовётся периодически из основного цикла
  reportFault(code, message, ctx) // сообщить о неисправности стандартным кодом
  assertGolden(name, actual, expected) // сверка с эталонным значением
  assertStateTransition(event, before, after, allowedDiffKeys) // см. ниже
  getStatus() -> {stage, faultCount}   // текущий статус, можно спросить в любой момент
}
```

Рабочий пример реализации на JS (можно адаптировать под другой язык/платформу) —
`templates/test-port.js`. Он уже содержит:
- обёртку над внешними/SDK-вызовами для фиксации реально произошедших событий;
- watchdog-таймер (heartbeat) — отличает "зависло" от "упало" от "не стартовало";
- структурированные коды неисправностей вместо текста в свободной форме.

## Коды неисправностей (аналог OBD-II)

Числовые коды вместо строк — чтобы можно было агрегировать статистику по типам
отказов, а не грепать текст. Рекомендуемая раскладка диапазонов (адаптируй под
свою область):

| Диапазон | Категория | Примеры |
|---|---|---|
| 1xx | Нарушение контракта/интерфейса | зависимость не найдена, метод отсутствует, метод не был вызван |
| 2xx | Ошибка в рантайме | необработанное исключение, rejected promise, ошибка в логе |
| 3xx | Неверный/отсутствующий вывод | пустой результат, не отрисовалось, файл не создан |
| 4xx | Логическая ошибка (golden vector) | детерминированный расчёт дал не то значение |
| 5xx | Проблема со временем | таймаут запуска (POST), зависание (watchdog), дедлок |

Полная таблица с описаниями — `templates/fault-codes.md`, синхронизируй её
вручную между кодом модуля и кодом тестового стенда (как таблица диагностических
кодов живёт на стороне сервисного оборудования, а не внутри самого узла).

## Тестовые тиры (от дешёвого к дорогому)

По аналогии wafer-level → package-level → system-level → burn-in в производстве
электроники — гоняй проверки от самых дешёвых к самым дорогим, чтобы не тратить
время на дорогой тест того, что уже провалилось на дешёвом:

1. **Синтаксис/статический анализ** (линтер, `--check`) — секунды, отсекает грубый брак.
2. **Контракт/манифест** — наличие файлов, обязательных полей, точки входа.
3. **POST в реальной среде выполнения** — модуль запускается, вызывает `markReady()`,
   отчитывается через `heartbeat()`. Тестовый стенд читает `TestPort`, а не лезет
   во внутренности.
4. **State-transition / property-based проверка** — прогон через таблицу переходов
   состояний (золотое правило выше), либо fuzz-тест случайными последовательностями
   событий, если таблица велика.
5. **Полевая телеметрия / канареечный релиз** — то, что вообще невозможно
   формализовать заранее (реальные пользователи, реальные данные), лечится не
   предрелизным тестом, а мониторингом в проде на малом % трафика.

Не пытайся заменить тир 5 более тяжёлым тиром 4 — какая-то доля багов
принципиально ловится только на реальном использовании, и это нормально.

## Чек-лист при старте нового модуля/программы

- [ ] Определён контракт `TestPort` (или его аналог) для этого класса модулей проекта
- [ ] Есть явная стадия "boot" с явным сигналом готовности (`markReady`), а не
      расчёт на угадывание таймаута
- [ ] Есть heartbeat/watchdog, если модуль имеет длительный жизненный цикл
      (не только "запустился/упал", но и "не завис")
- [ ] Заведены fault-коды (хотя бы черновой список диапазонов) вместо текстовых
      сообщений об ошибках "на глаз"
- [ ] Для детерминированной логики — хотя бы несколько golden vectors
- [ ] Для модулей с явным состоянием (state machine, флаги режимов, кэш) —
      составлена таблица переходов состояний, и тест сверяет **весь** снимок
      состояния до/после, а не только ожидаемое поле (см. золотое правило)
- [ ] Тестовый код физически отделён от продовой сборки (флаг сборки/окружения),
      как тестовый режим устройства не должен быть доступен конечному пользователю
