# Drift Check

После реализации сверить код с тем, что было обещано в планах и README. Расхождение — это не только «обещали и не сделали», но и «сделали и не обещали».

## Правило

1. Собрать список источников: планы, `SPEC.md`, README, задачи, комментарии в PR.
2. Разобрать каждый источник на **проверяемые утверждения** — по одному на строку.
3. Для каждого утверждения найти код, который его реализует: файл и место.
4. Пройти обратным ходом: найти код, которого нет ни в одном источнике.
5. Отдать таблицу расхождений с предложением по каждому.

## Формат отчёта

| Утверждение | Источник | Код | Статус |
|---|---|---|---|
| Повторный запуск даёт 0 изменений | `SPEC.md` I3 | `sync.js:41` | совпадает |
| Откат при расхождении после записи | `SPEC.md` I4 | — | **обещано, нет** |
| Кэш ответов на 5 минут | — | `api.js:88` | **есть, не обещано** |

Три статуса, четвёртого нет: `совпадает`, `обещано, нет`, `есть, не обещано`. «Примерно совпадает» — это расхождение.

## Почему обе стороны

Односторонняя проверка (только «что забыли») пропускает вторую половину проблемы: код, который никто не просил. Он выглядит безобидно, но это незапланированная поверхность — его не тестировали по требованиям, о нём не знает поддержка, и он переживёт рефакторинг, потому что непонятно, зачем существует.

## Примеры

### Плохо

❌ «Вроде всё сделали, тесты зелёные.»
Зелёные тесты отвечают на вопрос «работает ли то, что написано», а не «написано ли то, что обещано».

### Хорошо

✅ «Сверил `SPEC.md` и README с кодом: 11 утверждений, 9 совпадают, 2 расходятся.
Обещано, нет: откат при расхождении (`SPEC.md` I4), лимит 100 записей за запуск (R7).
Есть, не обещано: кэш ответов на 5 минут в `api.js:88` — предлагаю либо внести в спеку, либо убрать.»

## Когда не применять

- **Вместо тестов.** Drift-check сверяет код с намерением; работает ли код — показывают тесты. Нужны оба.
- **Когда источников нет.** Если план жил только в чате, сверять не с чем — сначала зафиксируйте план (`spec-driven-dev`), иначе проверка превратится в спор о памяти.
- **На середине работы.** Пока реализация идёт, расхождения — норма. Проверка имеет смысл на границе: фича готова, релиз, PR.

## Антипаттерны

- **Сверка по памяти.** «Я помню, что мы договаривались…» — источником должен быть файл, а не recollection.
- **Только чтение README.** README отстаёт первым; планы и спеки содержат то, что до README не дошло.
- **Список без адресов.** «Не хватает валидации» бесполезно; «не хватает валидации в `import.js`, обещано в R4» — actionable.
- **Расхождение без решения.** Каждая строка заканчивается выбором: починить код, поправить спеку или убрать лишнее.

## Чек-лист

- [ ] Собраны все источники: планы, спеки, README, задачи.
- [ ] Каждое утверждение разобрано на проверяемые пункты.
- [ ] Для каждого найдено место в коде (файл и строка) или зафиксировано отсутствие.
- [ ] Пройден обратный ход: код без источника.
- [ ] По каждому расхождению предложено решение, а не только констатация.
