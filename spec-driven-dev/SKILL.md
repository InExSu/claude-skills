# Spec-Driven Development

Спецификация первична, код производен. Код — перегенерируемый артефакт, спецификация — источник истины. Если поведение неверное, правят спецификацию и приводят код в соответствие, а не латают код вслепую.

## Принципы

1. **Что и в каких границах, а не как.** Спецификация фиксирует намерение, ограничения и проверки. Реализацию выбирает исполнитель, кроме жёстких ограничений.
2. **Границы важнее функции.** Функция обычно укладывается в 3 строки. Основной объём спецификации — что код **не имеет права** трогать (не-цели) и что **всегда** истинно (инварианты).
3. **Каждое требование проверяемо.** Если пункт нельзя проверить командой или тестом, он переписывается или вычёркивается.
4. **Неоднозначности закрыты до генерации.** Спорное место решено в спецификации либо записано как открытый вопрос с решением по умолчанию.
5. **Трассируемость.** Требования R, инварианты I, критерии приёмки A. Каждый тест ссылается на ID, каждый ID покрыт тестом.
6. **Безопасность по умолчанию.** Для кода, который пишет во внешние данные: dry-run по умолчанию, предохранитель на объём изменений, отказ при неоднозначности, идемпотентность.
7. **Минимальный след.** Новый код не меняет чужой код проекта. Лишний diff — нарушение приёмки.
8. **Спецификация живёт.** Любое исправление начинается с правки спецификации.

## Масштаб: сколько спецификации нужно

Подбери глубину до начала работы.

| Риск | Пример | Что делать |
|---|---|---|
| Низкий | чистая функция, утилита, чтение данных | мини-спека: цель, 3–7 критериев A, не-цели в 2–3 строки |
| Средний | сервис, парсер, API-клиент | полная спека по шаблону |
| Высокий | запись в чужие данные, деньги, удаление, cron, миграции | полная спека + обязательные разделы «Защита данных» и «План проверки» |

Если сомневаешься, бери уровень выше.

## Процесс

### Шаг 0. Разведка
- Прочитай существующий проект/код, если он есть: стек, версии, структура, стиль, как ведутся логи и секреты, есть ли готовый клиент для нужного API.
- Если нужно выбрать проект для размещения, выбирай тот, где уже есть нужная инфраструктура. Не создавай новый проект ради одного файла.
- Найди и перечитай пользовательские соглашения (coding-style, линтеры, шаблоны именования). Они становятся ограничениями спецификации.

### Шаг 1. Закрой неоднозначности
- Выпиши все места, где два исполнителя поняли бы задачу по-разному.
- Блокирующие вопросы (ответ меняет данные или архитектуру, а разумного умолчания нет) задай пользователю, не больше 3 за раз.
- Остальное реши сам и запиши в «Открытые вопросы» с пометкой «по умолчанию».
- Не спрашивай то, что можно узнать из кода или документации.

### Шаг 2. Напиши спецификацию
Используй шаблон ниже. Сохрани как `SPEC.md` рядом с кодом (или в `docs/`, если так принято в проекте). Для мини-спеки допустим комментарий-шапка в файле.

### Шаг 3. Проверь спецификацию до кода
Перед генерацией пройди чек-лист:
- Каждое R покрыто хотя бы одним A.
- Каждый инвариант I можно проверить автоматически (diff до/после, запрос, assert).
- Есть ответ на вопрос «что будет при пустых данных, дублях, огромном объёме, сбое посреди работы, повторном запуске, двух параллельных запусках».
- Не-цели названы явно, включая «похожие» объекты, которые легко затронуть случайно.
- Нет слов «быстро», «удобно», «корректно» без числа или проверки.

### Шаг 4. Тесты раньше кода
- Из критериев A сделай тесты (или проверочный скрипт, если фреймворка нет). Имя теста содержит ID: `test_A5_outside_section_untouched`.
- Покрой границы: пусто, один элемент, много страниц, дубли, спецсимволы и юникод, превышение лимитов, сбой сети, повторный запуск.
- Для внешних систем используй подмену (mock/fake). Реальные вызовы только в отдельной ручной проверке на тестовых данных.
- Покажи, что тесты падают без реализации, если это возможно.

## Шаг 4a. Детерминированные сценарии проверки (обязательно)

Любая проверка, которая может зависеть от случайности, времени, сети или порядка кадров, обязана иметь **детерминированный сценарий**. Иначе зелёный результат ничего не доказывает, а красный — неизвестно что.

Требования к сценарию:

1. **Seed.** Если код использует ГПСЧ, тест передаёт seed/фиксированный генератор. `Math.random()` внутри тестируемого кода — дефект тестируемости; вынеси генератор параметром.
2. **Фиксированные данные.** Трафик, очередь, список, время и позиции задаются явно, а не «что успело появиться за N секунд». Для игры — фиксированный набор сущностей, координат и скоростей.
3. **Телепорт/прямая установка состояния.** Вместо «подожди, пока игрок доедет» — установи `playerZ`, `screen`, позиции сущностей напрямую через тестовый хук. Ожидание допустимо только для проверки самого ожидания (загрузка, таймаут).
4. **Повторяемость.** Один и тот же сценарий, запущенный 3 раза, даёт один и тот же вердикт. Если нет — это флейк, а не тест.
5. **Явный сценарий провала.** Проверка должна уметь падать: подложи заведомо непроходимый кластер, неверный язык, скрытую вкладку. «Всегда зелёная» проба не считается проверкой.
6. **Порог по времени только там, где он измеряется.** Если критерий A говорит «за 30 с», тест не должен требовать того же события за 5 с.

Если сценарий детерминировать нельзя (внешний сервис, живой прод), отделяй два уровня: детерминированный офлайн-тест и отдельную полевую пробу, которая не входит в гейт.

## Шаг 4b. Автоматический аудит трассируемости R→A

Чек-лист «каждый R покрыт A» глазами не работает на длинной спецификации. Запускай аудит:

```
node scripts/spec_Trace_Audit.mjs <путь/к/spec.md>
```

Аудит обязан падать, если:
- есть `R` без хотя бы одного `A`;
- `A` ссылается на несуществующий `R`;
- ID `R`, `I` или `A` повторяются;
- таблица критериев пуста или не разбирается.

Аудит — часть шага 6 (приёмка), а не пожелание. Красный аудит блокирует мерж так же, как красный тест.

### Шаг 5. Генерация кода
- Пиши минимальную реализацию, которая проходит тесты и не нарушает инварианты.
- Конфигурация и секреты — из окружения, не из кода.
- Не добавляй функциональность, которой нет в спецификации. Идею «а ещё можно...» записывай в открытые вопросы.
- Для опасных операций порядок такой: прочитать, вычислить план изменений, проверить предохранители, записать, перечитать и сверить.

### Шаг 6. Приёмка
- Запусти тесты. Сообщай результат фактами: сколько прошло, что упало.
- Построй матрицу трассируемости: ID требования → тест → статус.
- Проверь инварианты на снимках «до/после», если есть возможность.
- Убедись, что diff по проекту ограничен заявленными файлами.
- Если что-то не проверено (нет доступа к системе, нет тестовых данных), так и скажи. Не заявляй «работает» без запуска.

### Шаг 7. Исправления и изменения
Порядок всегда один: найди пункт спецификации, который привёл к ошибке, или пробел в ней → поправь спецификацию → добавь/измени тест → поправь код → прогони всё. Баг, для которого нет теста, считается не исправленным.

## Шаблон спецификации

```markdown
# <Название>

## 1. Цель
Одно-два предложения: какой результат и зачем.

## 2. Контекст
Стек, окружение, откуда вызывается, откуда берутся данные, где размещается код.

## 3. Требования
- R1. ... (одно проверяемое утверждение на пункт, глаголы «должен», «не должен»)
- R2. ...

## 4. Не-цели (границы)
- Не трогать ...
- Не менять ...
- Не делать ...

## 5. Инварианты
- I1. После выполнения X для любого объекта значение A равно прежнему или f(прежнее).
- I2. Все остальные поля/объекты не изменились.

## 6. Защита данных   (обязательно, если код пишет вовне)
- Режим dry-run по умолчанию, запись по явному флагу.
- Предохранитель: максимум N изменений за запуск.
- Идемпотентность: повторный запуск даёт 0 изменений.
- Блокировка от параллельного запуска.
- Проверка после записи и откат при расхождении.
- Лог каждого изменения: ID, было, стало.

## 7. Конфигурация
Что берётся из окружения, какие константы и их значения по умолчанию.

## 8. Критерии приёмки
| № | Дано | Когда | Тогда | Покрывает |
|---|------|-------|-------|-----------|
| A1 | ... | ... | ... | R1 |

## 9. План проверки
1. На тестовых данных.
2. Dry-run на боевых, сверка отчёта.
3. Снимок до/после и автоматический diff (проверка I).
4. Включение боевого режима.
5. Детерминированный сценарий: seed, фиксированные данные, телепорт состояния, 3 повтора.
6. `node scripts/spec_Trace_Audit.mjs <spec.md>` — зелёный.

## 10. Открытые вопросы (с решением по умолчанию)
- Вопрос? **По умолчанию:** ...
```

## Библиотека проверок по типу задачи

Выбери нужное и добавь в спецификацию как R/A.

**Запись во внешние данные (CRM, БД, файлы):** отбор строго по явному условию; обновляются только перечисленные поля; предохранитель на объём; dry-run; снимок до/после; проверка кодировки и усечения (длина поля, 4-байтовые символы); повтор при 429/5xx с нарастающей задержкой; постраничный обход до конца; вторая параллельная копия не запускается.

**Периодические задачи (cron):** идемпотентность; блокировка с таймаутом; лог каждого запуска; поведение при пропущенных запусках; код возврата для мониторинга.

**API-клиенты:** таймауты; лимиты; повторы только для идемпотентных вызовов; разбор ошибок; секреты вне кода.

**Парсеры и преобразования:** пустой ввод, битый ввод, юникод, огромный ввод; сохранение исходных данных при ошибке.

**UI и игры:** состояния (загрузка, пусто, ошибка, успех); поведение при отказе ввода; проверка критического пути автотестом или режимом автопрохода.

## Антипаттерны

- Писать код, а спецификацию «восстанавливать потом».
- Критерии вида «работает корректно».
- Спецификация без не-целей для кода, который пишет в данные.
- Тест, который проверяет только то, что нужное произошло, и не проверяет, что ненужного не произошло.
- Молча принять решение по неоднозначности, не записав его.
- Чинить код при ошибочной спецификации.
- Расширять объём работы («заодно отрефакторил») без записи в спецификации.
- Заявлять приёмку без запуска проверок.

## Формат итогового ответа

Коротко: что сделано; где лежат `SPEC.md`, тесты и код; матрица «требование → тест → статус»; что не удалось проверить и почему; принятые решения по умолчанию, которые стоит подтвердить.

## Пример: мини-спека → тест → код

Задача: функция, которая читает CSV и возвращает массив объектов.

### Спека (мини, риск — низкий)

```markdown
# CSV reader

## Цель
Читать CSV-файл и возвращать массив объектов, где ключи — заголовки.

## Требования
- R1. Первая строка — заголовки, остальные — данные.
- R2. Пустые строки пропускаются.
- R3. Каждая строка данных становится объектом с полями из заголовков.

## Не-цели
- Не поддерживает экранирование запятых.
- Не поддерживает многострочные поля.

## Критерии приёмки
| № | Дано | Когда | Тогда | Покрывает |
|---|------|-------|-------|-----------|
| A1 | CSV: "a,b\n1,2\n3,4" | read("file.csv") | [{a:"1",b:"2"},{a:"3",b:"4"}] | R1,R3 |
| A2 | CSV с пустой строкой | read("file.csv") | пустая строка пропущена | R2 |
```

### Тесты (до кода)

```javascript
const { read } = require('./csv-reader.js');

test('A1: headers + 2 rows', () => {
  const result = read('a,b\n1,2\n3,4');
  expect(result).toEqual([{ a: '1', b: '2' }, { a: '3', b: '4' }]);
});

test('A2: empty lines skipped', () => {
  const result = read('a,b\n1,2\n\n3,4');
  expect(result).toEqual([{ a: '1', b: '2' }, { a: '3', b: '4' }]);
});
// До реализации: оба теста падают с "read is not a function".
```

### Код (минимальная реализация)

```javascript
function read(csv) {
  const lines = csv.split('\n').filter(l => l.trim() !== '');
  const headers = lines[0].split(',');
  return lines.slice(1).map(line => {
    const values = line.split(',');
    const obj = {};
    headers.forEach((h, i) => { obj[h] = values[i]; });
    return obj;
  });
}
module.exports = { read };
// Тесты проходят. Матрица: A1 ✓ (R1,R3), A2 ✓ (R2).
```
