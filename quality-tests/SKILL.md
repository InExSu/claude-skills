# Quality Tests Skill

Основан на серии статей «Бестолковые тесты versus качественное ПО» (Арсений Жижелев, Habr, 2023).
Центральная идея: **тесты — средство, не цель**. Качество ПО достигается комбинацией типов, архитектуры и тестов.

## §1 — Антипаттерны: чего НЕ писать

Прежде чем писать тест, убедись, что он не попадает в одну из категорий бестолковых тестов:

### Тавтологичные тесты
Тест воспроизводит логику проверяемого кода один-в-один.
```scala
// КОД
def config() = Config("a", 2)

// БЕСТОЛКОВЫЙ ТЕСТ — просто переписывает значения
assert(cfg.a == "a")
assert(cfg.b == 2)
```
**Признак**: если удалить тест и переписать конфиг, тест обновится автоматически.

### Тесты ради покрытия
Код вызывается, результат игнорируется.
```scala
def test() = f(0)  // без assert — покрытие есть, смысла нет
```

### Тесты-бухгалтеры
```scala
assert(routes().length == 10)  // сломается при любом добавлении роута
```

### Моки-тавтологии («алгоритм шиворот-навыворот»)
Когда mock повторяет логику тестируемого метода — тест проверяет только то, что метод вызывается, а не что он делает правильное.

### Глубокое тестирование чужого кода
Тестировать поведение БД/фреймворка/stdlib — не нужно. Доверяй библиотекам.

### Поверхностные HTTP-тесты
```scala
assert(response.status == 200)  // только статус, без проверки тела
```

## §2 — Что тест должен проверять

Бизнес и менеджеры ожидают от тестов четыре вещи:

1. **Раннее обнаружение** — ошибка находится до прода.
2. **Защита рефакторинга** — сломанная функция роняет хотя бы один тест.
3. **Модульность кода** — тесты заставляют делать код тестируемым (→ лучше архитектура).
4. **Документация** — тест показывает, как пользоваться API на рабочих примерах.

**Правило**: перед написанием теста задай вопрос — *какое из четырёх свойств выше этот тест обеспечивает?* Если ни одно — тест, скорее всего, бестолковый.

## §3 — Как писать осмысленные тесты

### 3.1 Тестируй поведение, не реализацию

Тест должен проверять **что** делает функция, а не **как**.

```scala
// ПЛОХО: тест знает про внутренний вызов inc()
mock.expectSequence { mock.inc(); mock.inc() }

// ХОРОШО: тест проверяет результат
assert(counter.incrementTwice().value == 2)
```

### 3.2 Граничные случаи — только там, где есть ветвление

Граничные тесты нужны ровно там, где код ветвится. Используй цикломатическую сложность как ориентир: **минимальное количество тестов = цикломатическая сложность функции**.

Если функция прямолинейна (нет `if`/`match`/циклов) — достаточно одного теста.

### 3.3 Property-based тесты для алгоритмических функций

Вместо таблицы конкретных примеров — проверяй инварианты:
```scala
// Для функции сортировки:
forAll { list: List[Int] =>
  val sorted = sort(list)
  sorted.length == list.length          // размер не меняется
  sorted.zip(sorted.tail).forall(_ <= _) // каждый элемент ≤ следующего
  sorted.toSet == list.toSet             // элементы те же
}
```

### 3.4 Тесты на примеры нарушений требований

Когда найден баг — сначала тест, воспроизводящий его, потом исправление:
```scala
// Регрессионный тест: баг #42 — отрицательный userId падал с NPE
test("userId не может быть отрицательным") {
  assertThrows[ValidationError](processUser(userId = -1))
}
```

### 3.5 Интеграционные тесты — на швах системы

Тестируй компоненты там, где они соединяются, а не глубоко внутри каждого.
Конфигурируй SUT (system under test) так, чтобы она была как можно ближе к боевому режиму.

## §4 — Чем заменить тесты (когда тип сильнее теста)

Многие классы ошибок устраняются типами дешевле, чем тестами:

| Класс ошибки | Инструмент | Тест нужен? |
|---|---|---|
| Опечатки, несуществующие методы | Компилятор (статическая типизация) | Нет |
| NPE / null | `Option`, `Either`, Kotlin `?`, Scala `-Yexplicit-nulls` | Нет |
| Выход за диапазон (порт > 65535) | Refined types / value classes | Нет |
| Невалидные данные в бизнес-логике | ADT + parse-don't-validate | Нет |
| Выход за границы массива | `map`/`filter`/`fold` вместо цикла | Нет |
| Некорректное состояние (протокол) | Make illegal states unrepresentable | Нет |
| Нарушение требований | **Тесты** | Да |
| Ошибка понимания требований | Код-ревью + acceptance tests | Да |

**Принцип parse-don't-validate**: на входе системы — валидация в тип, дальше — только валидный тип.

```scala
// ПЛОХО: String летит через всю систему, везде нужна проверка
def processPort(port: String): Unit = ...

// ХОРОШО: валидный тип — один раз на входе
case class Port private(value: Int)
object Port {
  def parse(n: Int): Either[String, Port] =
    if (n > 0 && n < 65536) Right(Port(n)) else Left(s"Invalid port: $n")
}
def processPort(port: Port): Unit = ...  // тут уже нечего проверять
```

## §5 — Уменьшение количества тестов через «распрямление» кода

Чем меньше ветвлений — тем меньше нужно тестов.

### Убирай boolean-флаги → enum + паттерн Стратегия

```scala
// ПЛОХО: нужно 2 набора тестов
def adjust(value: Int, useHi: Boolean): Int = ...

// ХОРОШО: ветвление выносится в конфигурацию
def adjust(value: Int, level: => Int): Int = level - value
```

### Option/Either вместо ветвления на ошибках

```scala
// Цикломатическая сложность эффективно = 1, ветвление — в библиотеке
def flow(input: Option[Int]): Option[Int] =
  input.flatMap(step1).flatMap(step2).map(step3)
```

### map/flatMap вместо циклов

```scala
// Вместо цикла с индексом (и возможным off-by-one)
val result = items.filter(_.isValid).map(transform).foldLeft(zero)(combine)
```

## §6 — Чеклист перед коммитом тестов

- [ ] Тест проверяет **поведение** (не внутренний механизм)?
- [ ] Тест упадёт, если код сломается по-настоящему?
- [ ] Тест можно понять без чтения реализации?
- [ ] Тест не дублирует логику тестируемого кода?
- [ ] Количество тест-кейсов ≈ цикломатической сложности функции?
- [ ] Нельзя ли заменить этот тест типом данных?
- [ ] Есть граничный случай — есть тест для каждой стороны границы?

## Быстрая ссылка: что тестировать в проекте

```
Бизнес-логика с ветвлениями          → юнит-тесты на каждую ветку
Алгоритмические функции              → property-based тесты
Интеграция с внешними системами      → интеграционные тесты на швах
Пользовательские сценарии (happy path + key failures) → acceptance тесты
Граничные условия входных данных     → юнит-тесты + refined types
Конфигурация системы                 → компилируемая конфигурация (если возможно)
```
