## §1 — Антипаттерны: чего НЕ писать

### Тавтологичные тесты
Тест воспроизводит логику кода один-в-один.
```js
// КОД: config() = { a: 'a', b: 2 }
// БЕСТОЛКОВЫЙ ТЕСТ:
assert(config.a === 'a')
assert(config.b === 2)
```
**Признак**: если удалить тест и переписать конфиг — тест обновится автоматически.

### Тесты ради покрытия
Код вызывается, результат игнорируется (`f(0)` без `assert`).

### Тесты-бухгалтеры
`assert(routes.length === 10)` — сломается при любом изменении.

### Моки-тавтологии
Mock повторяет логику тестируемого метода — проверяет только вызов, а не правильность.

### Поверхностные HTTP-тесты
`assert(response.status === 200)` — только статус, без тела.

## §2 — Что тест должен проверять

Тесты должны обеспечивать 4 вещи:
1. **Раннее обнаружение** — ошибка до прода
2. **Защита рефакторинга** — сломанная функция роняет тест
3. **Модульность** — тесты заставляют делать код тестируемым
4. **Документация** — тест показывает, как пользоваться API

**Правило**: перед тестом спроси — *какое из 4 свойств он обеспечивает?*

## §3 — Как писать осмысленные тесты

### Тестируй поведение, не реализацию
```js
// ПЛОХО: тест знает про внутренний вызов
mock.expectSequence(() => { mock.inc(); mock.inc() })

// ХОРОШО: тест проверяет результат
assert(counter.incrementTwice().value === 2)
```

### Граничные случаи — только где есть ветвление
Минимальное количество тестов ≈ цикломатическая сложность функции.

### Property-based для алгоритмов
```js
// Для сортировки:
forAll(list => {
  const sorted = sort(list)
  sorted.length === list.length
  sorted.every((x, i) => i === 0 || x >= sorted[i-1])
  new Set(sorted) === new Set(list)
})
```

### Тест на найденный баг
Сначала тест, воспроизводящий баг, потом исправление.

### Интеграционные тесты — на швах
Тестируй соединения компонентов, а не глубину каждого.

## §4 — Чем заменить тесты

Многие ошибки дешевле предотвращать типами:

| Ошибка | Инструмент | Тест? |
|--------|------------|-------|
| Опечатки | Статическая типизация | Нет |
| null | Option/Optional | Нет |
| Выход за диапазон | Refined types | Нет |
| Невалидные данные | ADT + parse-don't-validate | Нет |
| Выход за границы | map/filter/fold | Нет |
| Некорректное состояние | Make illegal states unrepresentable | Нет |
| Нарушение требований | **Тесты** | Да |
| Ошибка понимания требований | Code review + acceptance | Да |

**parse-don't-validate**:
```js
// ПЛОХО: string летит везде
function processPort(port) { ... }

// ХОРОШО: валидный тип — один раз на входе
class Port {
  static parse(n) {
    if (n > 0 && n < 65536) return { ok: true, value: new Port(n) }
    return { ok: false, error: 'Invalid port' }
  }
}
function processPort(port) { ... } // тут уже нечего проверять
```

## §5 — Уменьшение тестов через «распрямление»

Меньше ветвлений → меньше тестов.

### Boolean-флаги → enum + Strategy
```js
// ПЛОХО: 2 набора тестов
function adjust(value, useHi) { ... }

// ХОРОШО: ветвление в конфигурацию
function adjust(value, level) { return level - value }
```

### Option вместо ветвления на ошибках
```js
function flow(input) {
  return input
    .flatMap(step1)
    .flatMap(step2)
    .map(step3)
}
```

### map/filter вместо циклов
```js
// Вместо цикла с индексом
const result = items
  .filter(x => x.isValid)
  .map(transform)
  .reduce(combine, zero)
```

## §6 — Чеклист перед коммитом

- [ ] Тест проверяет **поведение**, не реализацию?
- [ ] Тест упадёт при реальной поломке?
- [ ] Тест понятен без чтения кода?
- [ ] Тест не дублирует логику тестируемого кода?
- [ ] Количество тестов ≈ цикломатической сложности?
- [ ] Нельзя заменить тест типом данных?
- [ ] Для каждого граничного случая есть тест?
