# Как контрибьютить

Спасибо за желание улучшить эти скиллы. Вклад любого размера приветствуется: исправленная опечатка, более точная фраза-триггер, новый скилл или инструментарий для существующего.

**English version:** [CONTRIBUTING.md](CONTRIBUTING.md)

Отправляя pull request, вы соглашаетесь, что ваш вклад распространяется под [лицензией MIT](LICENSE), покрывающей этот репозиторий.

---

## Что такое скилл

Скилл — это папка в корне репозитория с файлом `SKILL.md`:

```markdown
---
name: my-skill
description: >
  Точные условия срабатывания — когда применять и, что не менее важно, когда НЕТ.
---

# My Skill

## Правила
...
```

Claude Code сканирует папки в поисках `SKILL.md` и читает `name` + `description` из YAML-frontmatter. Если папка есть — скилл установлен: ни реестра, ни файла конфигурации нет.

Обязательные ключи frontmatter:

| Ключ | Правила |
|---|---|
| `name` | Совпадает с именем папки, в нижнем регистре, слова через `-`. |
| `description` | Самая важная часть скилла — см. ниже. |
| `allowed-tools` | Необязателен. Ограничивает доступные скиллу инструменты, например `Read, Write, Edit`. |

## Как писать работающее описание

`description` — это не документация, а **правило сопоставления**, от которого зависит, загрузится скилл или нет.

- Охватывайте реальные формулировки, которые наберёт человек, — и по-русски, и по-английски, если скилл применим к обоим языкам: *«исправь баг»*, *«fix this bug»*.
- Явно перечисляйте исключения. `tdd-bugfix` прямо говорит, что его нельзя применять для новых фич; `noosphere` — что чистые функции не должны зависеть от `ns`.
- Пишите «Не применять без явной активации», если скилл меняет поток управления или стиль именования, а не исправляет дефект.
- Держитесь одного абзаца: frontmatter загружается в контекст в каждой сессии.

## Правила к содержанию

1. **Требуйте, а не советуйте.** Проверяемое правило лучше рекомендации. Сравните «возможно, стоит вынести условие» и «условие с более чем тремя операторами обязано быть вынесено».
2. **Показывайте плохое и хорошее.** Пары «до/после» весомее абстрактных принципов.
3. **Указывайте область применения.** Отмечайте язык или фреймворк, чтобы скилл не протекал в чужую работу.
4. **Не дублируйте.** Сначала посмотрите [каталог скиллов](README.ru.md#-каталог-скиллов): расширить существующий скилл часто лучше, чем добавить почти такой же.
5. **Помещайтесь в один файл.** Скилл должен читаться за один подход. Нужна глубина — добавьте папку `reference/`, как сделано в `drakonhub`.

## Инструментарий и скрипты

`drakonhub` — единственный скилл с исполняемым кодом.

- Python 3, **только стандартная библиотека** — никаких сторонних зависимостей.
- Каждый скрипт обязан сохранять usage-докстринг в шапке модуля: запуск `python3 scripts/<имя>.py` без аргументов печатает `__doc__`.
- Скрипты должны быть детерминированными и не создавать побочных эффектов за пределами путей, переданных пользователем.

Перед открытием pull request прогоните проверки, которые уже есть в репозитории:

```bash
cd drakonhub
python3 scripts/drakon_tool.py check templates/choice-and-loop.drakon
python3 scripts/drakon_dsl.py roundtrip templates/minimal.drakon
python3 scripts/drakon_render.py svg templates/silhouette.drakon /tmp/out.svg
```

Все три должны ответить `OK`. Важнейшая — `roundtrip`: она конвертирует `.drakon` → DSL → `.drakon` и сверяет графы, поэтому правка конвертера, ломающая связи, ловится сразу.

## Процесс pull request

1. Сделайте форк и ветку: `git checkout -b add/my-skill`.
2. Внесите изменение. Один скилл или одна тема на pull request.
3. Обновите [каталог скиллов](README.ru.md#-каталог-скиллов) в **обоих** файлах — `README.md` и `README.ru.md`: таблицы и счётчик в значке `skills-N` живут там.
4. Прогоните проверки выше, если правка касается `drakonhub`, и вставьте их вывод в описание pull request.
5. Откройте pull request. Опишите, **какую проблему решает скилл** и **когда он не должен срабатывать** — именно это нужнее всего на ревью.

### Что ускоряет merge

- Чёткая постановка проблемы: какой режим отказа предотвращает скилл.
- Описание, построенное на живых формулировках, а не на выдуманных примерах.
- Отсутствие постороннего форматного шума в файлах, которых правка не касалась.

### Что, скорее всего, отклонят

- Скилл, пересказывающий общие добрые практики без проверяемого правила.
- Скилл, чьё описание подходит ко всему и грузится в каждой сессии.
- Сторонние зависимости в скриптах `drakonhub`.
- Закоммиченные `.DS_Store`, бэкапы редакторов, артефакты сборки — см. [.gitignore](.gitignore).

## Как сообщить о проблеме

По багу в скрипте откройте issue с точной командой, файлом, на котором она запускалась, и выводом, который вы получили и ожидали. По неожиданному поведению скилла приложите запрос, который вы сделали, и то, что скилл сделал вместо этого.
