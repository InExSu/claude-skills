# Range Prompt

Описывать приложение по тому, **что оно делает для людей**, а не по тому, **из чего оно собрано**. Затем развести субагентов по названным областям.

## Правило

1. Описать приложение глаголом: «его работа — X».
2. Перечислить области, по которым пойдёт ревью, — до запуска субагентов.
3. Дать каждому субагенту одну область и право предлагать исправления.

## Почему через глагол

«React + Express + Postgres» — это состав, из него не выводится, что важно. «Его работа — помогать мастеру записывать клиентов и не терять заявки» сразу задаёт, что считать дефектом: потерянную заявку, лишний клик при записи, непонятный статус.

Из глагольного описания области вытекают сами: запись клиента, сохранность заявок, статусы, уведомления.

## Примеры

### Ревью приложения

❌ «Проведи ревью приложения. У нас React + Express + Postgres.»
✅ «Его работа — помогать мастеру записывать клиентов и не терять заявки. Посмотри на него с максимального числа углов: путь записи от клика до подтверждения, сохранность заявки при сбое, понятность статусов, скорость на слабом телефоне, права доступа мастера и администратора.»

### Улучшение

❌ «Улучши наш сервис.»
✅ «Сервис помогает фрилансеру выставлять счёт за 2 минуты. Разведи субагентов по областям: время до первого счёта, ошибки в реквизитах, повторные счета, экспорт, мобильная вёрстка. Каждый предлагает и внедряет правки в своей области.»

## Почему области — заранее

Если области не названы до запуска, каждый субагент строит свою модель приложения и они проверяют одно и то же. Итог — пять отчётов про вёрстку и ни одного про потерю данных.

Практическое правило: **3–6 областей**. Меньше — узко, больше — отчёты некому свести.

## Когда не применять

- **Один конкретный вопрос про один файл.** «Почему падает тест в `cart.test.js`» — это прямая правка, субагенты добавят шум.
- **Нет возможности запустить субагентов.** Тогда честно дайте пользователю список областей и попросите прогнать их отдельно.
- **Приложение ещё не существует.** Обозревать нечего; сначала спека (`spec-driven-dev`).

## Антипаттерны

- **Описание составом.** «У нас монорепа на Nx» — ревью уйдёт в структуру папок вместо поведения.
- **Субагенты без областей.** Все смотрят на всё, находят очевидное, дублируют друг друга.
- **Области по слоям кода** (фронтенд, бэкенд, база) вместо областей по пользовательским задачам — так теряются сквозные дефекты, которые как раз и опасны.
- **Субагенты без права чинить.** Отчёт «надо бы поправить» без правок перекладывает работу обратно на человека.

## Чек-лист

- [ ] Приложение описано через действие (глагол), понятное постороннему.
- [ ] Области перечислены до запуска субагентов (3–6).
- [ ] Области — по пользовательским задачам, не по слоям кода.
- [ ] У каждого субагента одна область и право предлагать и внедрять исправления.
- [ ] Отчёты сведены в один документ, а не отданы пятью файлами.
